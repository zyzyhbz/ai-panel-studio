## 1. 产品定义

### 1.1 一句话

> 用户输入一个议题，系统生成一组立场互补的主持人与专家，实时演出一场有碰撞、有共识、有分歧、可回放的 AI 圆桌。

### 1.2 产品北极星

> 让用户用一句话发起一场 4–6 人的 AI 圆桌，在几分钟内看到多视角碰撞、实时共识/分歧和可回放的结构化结论，并能并行管理多个议题。

### 1.3 产品定位

「AI Panel Studio」是一个本地运行的 AI 圆桌演播厅 Web App，不是聊天机器人，也不是会议纪要工具。

它要解决的不是“让 AI 回答问题”，而是：

- 让不同立场的 Agent 真正互相听见、互相反驳
- 让讨论过程可见、可感、可回放
- 让用户不读完整 transcript 也能抓住共识、分歧和未决问题
- 让多个议题同时推进而互不污染

### 1.4 成功标准

MVP 成功不是“功能列表全”，而是：

1. 用户能在 30 秒内看懂首页在发生什么。
2. 进入演播厅后，能感觉“有人在主持、有人在抢话”，而不是机械轮播。
3. 不读全文，也能从右侧/下方看懂当前共识与分歧。
4. 结束后能完整回放，且回放与直播一致。
5. 同时开两个议题，事件、上下文、结论不串线。
6. 全流程不暴露 API Key、不展示隐藏 CoT、不展示原始 JSON。

## 2. 目标与非目标

### 2.1 目标

| 目标 | 说明 |
| --- | --- |
| 快 | 流式输出、短发言、低等待；不出现整段空白等待 |
| 全 | 立场/维度覆盖可感知，主持人主动补位，不承诺穷尽 |
| 结构化 | 共识、分歧、待验证问题实时可视化 |
| 可回放 | 语义事件持久化，直播/回放共用状态还原 |
| 可管理 | 多议题并行，状态/进度/结论清晰，严格隔离 |
| 可信 | 共识有发言依据，公开意图但不出卖隐藏 CoT |

### 2.2 P0 / P1 / P2

**P0（交付底线，缺一不可）**

- 首页讨论列表、创建讨论
- 主持人 + 专家阵容生成、确认
- 演播厅直播、自主发言、主持人开场/追问/串联/收尾
- 专家状态小窗
- 现场 transcript
- 实时共识/分歧/待验证问题
- 主持人自然语言总结
- 事件回放（暂停/倍速/跳转）
- 多讨论并行隔离
- SSE 实时更新
- SQLite 持久化 + 初始化脚本 + 5 条样例
- 中文 UI、三档响应式、区域独立滚动
- API Key 仅服务端
- mock LLM 模式与自动化测试

**P1（有时间才做）**

- 导出 Markdown/JSON
- 首页搜索/筛选
- 立场图谱
- 从共识/分歧跳转到对应发言
- 重新生成单个专家
- 暂停/继续讨论
- 议题模板

**P2（明确不做）**

- 视频/音频录制与导出
- 语音输入/语音合成
- 登录、权限、多租户
- 多人协作编辑
- 云端部署/横向扩展
- 议题树/子议题
- 联网搜索、工具调用、RAG

## 3. 用户与场景

### 3.1 目标用户

| 用户 | 场景 | 核心诉求 |
| --- | --- | --- |
| 知识工作者/研究人员 | 快速了解一个议题的多方观点 | 几分钟内拿到不同视角与争议摘要 |
| 产品/决策人员 | 方案评审前预演立场与争议 | 发现盲点、检验假设、提升决策质量 |
| 教育与内容创作者 | 把复杂议题结构化呈现 | 获得可回放、可引用的“虚拟专家访谈” |

### 3.2 核心用户故事

1. 作为研究者，我想输入一个议题并立刻看到一场多角色讨论，以便快速建立全局理解。
2. 作为决策者，我想看到专家之间的真实分歧和未决问题，以便发现自己的盲点。
3. 作为内容创作者，我想回放并引用某位专家的发言，以便整理成内容素材。
4. 作为演示者，我想同时开多个议题，以便对比不同讨论的进展和结论。

### 3.3 非目标用户

- 需要真实人类专家在线访谈的用户
- 需要法律/医疗等高风险决策结论的用户
- 需要多人实时协作编辑的团队

## 4. 核心概念与数据

### 4.1 概念

| 概念 | 定义 |
| --- | --- |
| Discussion（讨论） | 一个议题对应一个讨论会话；MVP 不做议题树 |
| Host（主持人） | 负责开场、追问、串联、收尾的 Agent，中立 |
| Expert（专家） | 有姓名、职业、Title、立场、专属颜色的 Agent |
| Message（发言） | 一次发言，1–2 句；有 speaker、内容、意图、序号 |
| Insight（洞察） | 共识 / 分歧 / 待验证问题；必须能关联到发言依据 |
| Event（事件） | 会话内不可变事实；回放的唯一数据源 |
| Replay（回放） | 从事件重建状态，不调用 LLM |

### 4.2 状态机

```text
generating → ready → live → summarizing → ended
                         ↘ failed
```

- `generating`：正在生成主持人与专家
- `ready`：阵容已生成，等待用户确认
- `live`：讨论进行中
- `summarizing`：主持人正在总结
- `ended`：已结束，可回放
- `failed`：生成/运行失败；有发言时可结束并回放，无发言时可重新生成

> 不对外暴露 `draft`；创建接口直接进入 `generating`。

### 4.3 数据实体（逻辑）

| 实体 | 关键字段 |
| --- | --- |
| Discussion | id, topic, status, expert_count, turn_count, planned_turns, max_turns, last_seq, error, created_at, updated_at, ended_at |
| Expert | id, discussion_id, role(host/expert), name, profession, title, stance, stance_axis, polarity, focus_area, color, sort_order |
| Message | id, discussion_id, expert_id, content, char_count, intent, target_message_id, references_json, degraded, turn_index, created_at |
| Insight | id, discussion_id, type(consensus/divergence/open_question), content, first_seen_turn, evidence_message_ids, updated_at |
| Event | id, discussion_id, seq, type, payload_json, created_at |
| Summary | discussion_id, content, is_fallback, created_at |

> 事件是事实源；`Message` / `Insight` / `Summary` 是可重建的投影。具体 schema 以 [ER 图](ER.md) 与 [G1 契约决议](06-G1契约决议.md) 为准。

## 5. 用户流程

### 5.1 首页 → 创建 → 阵容 → 直播

```text
首页
  ├─ 查看进行中/已结束讨论
  ├─ 点击进行中 → 进入直播
  ├─ 点击已结束 → 进入回放
  └─ 发起新讨论
        ↓
输入议题 + 选择专家人数（3–6，默认 4）
        ↓
生成主播 + 专家阵容（姓名/职业/Title/立场/颜色）
        ↓
用户确认阵容
        ↓
进入演播厅，倒计时 1.5s，主持人开场
        ↓
专家自主举手/抢答/补充/反驳
        ↓
实时 transcript + 共识/分歧 + 专家状态
        ↓
主持人总结 → ended
        ↓
回放 / 返回首页
```

### 5.2 多讨论并行

```text
首页 → 讨论 A 直播
     → 返回首页（A 继续在后台运行）
     → 讨论 B 直播
     → 首页显示 A/B 各自状态与进度
```

- 离开页面不等于结束讨论。
- 只有用户主动“结束讨论”或讨论自然结束，才进入 `ended`。
- 同一浏览器可同时打开多个标签页观察不同讨论。

### 5.3 回放

```text
首页/结束页 → 回放
  → 时间线从 0 开始
  → 播放/暂停/1x/1.5x/2x/跳转
  → 不调用 LLM
  → 与直播相同的 transcript/共识/状态
```

## 6. 功能需求（FR）

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 首页展示讨论列表 | 卡片含议题、状态、专家数、进度、更新时间、结论摘要（已结束）；点击进行中进直播，已结束进回放；空态有创建入口 |
| FR-02 | 创建讨论 | 议题必填 2–200 字；专家人数 3–6，默认 4；`clientRequestId` 幂等；提交后进入 generating；重复提交返回同一讨论；失败可重试且保留 discussionId |
| FR-03 | 生成阵容 | 1 位主持人 + N 位专家；每人有姓名、职业、Title、立场、`stanceAxis`、`polarity`、`focusArea`、专属颜色；颜色不重复；姓名/人设不重复；至少 3 种不同立场 |
| FR-04 | 阵容确认 | 用户可确认或重新生成；确认后进入 live；重复确认不重复启动；返回首页后未确认的阵容仍可继续 |
| FR-05 | 演播厅布局 | 桌面含议题栏、专家栏、transcript、共识/分歧栏；区域独立滚动；页面本身不滚动；三档屏宽合理 |
| FR-06 | 自主发言 | 主持人开场；专家根据当前 transcript 自主决定发言顺序；不出现固定轮转；每人每次 1–2 句；结束由观点饱和决定，轮次只做覆盖保底（`min(12,2n+2)`）与 36 轮安全上限 |
| FR-07 | 专家状态 | 每位专家显示 idle/preparing/speaking；显示当前关注点或公开思考摘要；不显示隐藏 CoT |
| FR-08 | 现场 Transcript | 显示发言人姓名、职业/Title、专属色块、发言内容；按时间顺序；不显示“举手”等内部事件；自动滚动，用户上滚后暂停并出现“跳到最新” |
| FR-09 | 实时共识/分歧 | 共识、分歧、待验证问题三个区域；讨论中增量更新；每条有依据发言数/引用；不重复堆叠；不编造一致 |
| FR-10 | 主持人总结 | 结束时以自然语言总结共识、分歧、未决问题；不显示 JSON；总结持久化，首页/回放可见 |
| FR-11 | 回放 | 支持播放/暂停/1x/1.5x/2x/跳转；刷新/重启后仍可回放；回放不调用 LLM；直播与回放内容一致 |
| FR-12 | 多讨论并行 | 同时运行至少 2 个讨论；事件流、transcript、共识、结论互不串线；首页在 visible 时每 5s 轮询，状态独立更新 |
| FR-13 | 结束/离开 | 用户可主动结束；结束后进入 summarizing/ended；失败且有发言的讨论也可结束并回放；离开页面不取消后台讨论；结束后不可继续发言 |
| FR-14 | 样例数据 | 数据库初始化脚本 + 至少 5 条高质量样例（预设议题 + 对应 1 主持 + 4 专家阵容）；覆盖 5 种状态；字段非空、颜色唯一、立场 ≥3 类；至少 1 条含 ≥8 轮 transcript + ≥2 条洞察 + 总结，可直接回放 |
| FR-15 | 异常与空态 | 生成失败、LLM 超时、SSE 断线、空列表、无共识均有可读状态；`discussion.failed` 可见；总结失败允许 `summary=null` 的 ended；不显示原始堆栈/JSON；SSE 自动重连 |
| FR-16 | Key 安全 | API Key 只在服务端环境变量；前端 bundle/网络响应/日志均不出现 Key |
| FR-17 | 一键运行 | Windows 下按 README 可完成安装、迁移、种子、启动；提供 `.env.example` |

## 7. AI 行为需求（AR）

| ID | 需求 | 验收标准 |
| --- | --- | --- |
| AR-01 | 人设多样性 | 专家在职业、立场、关注点上互补；主持中立；不出现 4 个同质化“专家” |
| AR-02 | 主持人职责 | 开场点题；至少 1 次追问；至少 1 次串联不同专家；结尾总结；不长期霸占发言 |
| AR-03 | 发言调度 | 基于当前 transcript 决定下一位；意图为 opening/probe/rebut/support/extend/clarify/mediate/redirect/summary；用 `references` 表达串联；禁止固定顺序轮转；同一专家不连续超过 2 次；举手/抢答是行为效果，不作为 transcript 内部事件 |
| AR-04 | 发言长度 | 每次 1–2 句；单条不超过约 120 个中文字符；不写成小作文 |
| AR-05 | 上下文工程 | 每次发言使用最新 transcript 窗口 + 结构化摘要 + 当前共识/分歧 + persona + 轮次计划；只读本会话；不跨会话 |
| AR-06 | 公开透明 | 对外只暴露状态、`focusArea`/`turnFocus`、发言意图等公开字段；不展示 `reasoning_content`/隐藏 CoT；transcript 不显示“举手”等内部事件 |
| AR-07 | 共识依据 | 每条共识/分歧至少关联 1 条发言；没有明确依据时放入“待验证”，不编造 |
| AR-08 | 总结质量 | 自然语言；覆盖共识、分歧、未决问题；不出现 JSON 字段名/原始结构 |
| AR-09 | 失败降级 | 超时/无效 JSON/空输出时有兜底：重试一次、跳过该轮或使用安全文案；不卡死、不白屏 |
| AR-10 | 模型约束 | 实时链路默认 `deepseek-flash` 且关闭 thinking；模型可配置；单场成本目标 < ¥1 |
| AR-11 | 行为评测 | 至少 5 个议题的离线 eval；记录 JSON 合法率、发言长度、发言分布、重复率、共识依据、延迟、成本 |

## 9. 界面与交互

### 9.1 视觉方向

关键词：**演播厅、聚光灯、深色舞台、专家色、实时感、克制的科技感**。

避免：通用后台管理面板、聊天窗口堆叠、纯白 SaaS 卡片墙、过度霓虹。

建议：

- 背景：深炭灰/近黑，局部聚光渐变
- 强调色：暖金 + 青绿，用于“直播/共识/分歧”状态
- 专家色：每人一个专属色，用于头像、边框、发言标记
- 字体：中文无衬线，标题有舞台感，正文保证可读
- 动效：发言者聚光、消息入场、状态脉冲；尊重 reduced motion

### 9.2 桌面布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 议题标题 / 状态 / 进度 / 结束讨论                             │
├───────────────┬──────────────────────────┬───────────────────┤
│ 专家状态栏     │ Transcript（主区域）      │ 共识 / 分歧 / 待验证 │
│ host + experts │ 独立滚动                  │ 独立滚动            │
│ 状态/关注点    │                          │ 依据/引用           │
├───────────────┴──────────────────────────┴───────────────────┤
│ 直播状态 / 轮次 / 回放控件 / 跳到最新                          │
└──────────────────────────────────────────────────────────────┘
```

### 9.3 响应式

- **≥1440**：三栏 + 顶部议题栏 + 底部控制条
- **1024–1439**：左栏收窄，右栏可折叠为抽屉
- **768–1023**：两栏，共识/分歧为右侧抽屉
- **<768**：单栏 + 底部 Tab（讨论 / 专家 / 共识），各 Tab 独立滚动

硬规则：

- `body` 不整体滚动
- 每个面板 `overflow: auto`，高度用 grid/flex 约束
- 不依赖 hover 才能完成关键操作
- 移动端输入框不被键盘遮挡

### 9.4 关键状态

- 首页：loading / empty / list / error
- 创建：idle / validating / generating / ready / failed
- 直播：connecting / live / reconnecting / ended
- 回放：paused / playing / seeking / ended
- 共识：empty / updating / populated

## 10. API、事件与数据约束

### 10.1 API 原则

- REST 负责命令与查询；SSE 负责实时事件。
- 所有请求/响应有 Zod 契约；错误统一 `{ error: { code, message } }`。
- 资源按 `discussionId` 隔离；禁止无会话条件的全表操作。
- 不在 API 中返回隐藏 CoT、原始 LLM JSON、API Key。

### 10.2 核心接口（草案）

```text
GET    /api/discussions
POST   /api/discussions
GET    /api/discussions/:id
GET    /api/discussions/:id/state
POST   /api/discussions/:id/roster/regenerate
POST   /api/discussions/:id/confirm
POST   /api/discussions/:id/end
GET    /api/discussions/:id/events?after=seq
GET    /api/discussions/:id/stream        # SSE
GET    /api/health
```

详细字段见 [API 契约](03-API契约.md) 与 [SSE 事件契约](04-SSE事件契约.md)。

### 10.3 事件原则

- 每个会话独立 `seq`，从 1 递增。
- 事件不可变；投影可重建；`events.payload_json` 就是 SSE `data` 对象。
- 直播发送 token delta；落库只存完整消息等语义事件。
- 每个 `turn.started` 必须有 `message.completed` 或 `turn.aborted`。
- 每个会话必须有终态：`discussion.ended` 或 `discussion.failed`。
- 回放按 `seq` 重放；不调用 LLM。
- SSE 支持 `Last-Event-ID` 补发与 `stream.caught_up`。

### 10.4 关键约束

- 同一会话发言串行；不同会话可并行。
- 同一专家不连续超过 2 次。
- 结束由观点饱和决定；轮次只做覆盖保底（每位专家≥2次）与 36 轮安全上限，不作为目标。
- 结束后不再产生新发言。
- 任何 LLM 失败都不能让会话永久卡在 `live`。

## 11. 验收与测试

### 11.1 主链路 E2E

```text
首页 → 创建议题 → 生成阵容 → 确认 → 直播
→ 至少 8 轮发言 → 共识/分歧更新 → 总结
→ 回放 → 暂停/倍速/跳转 → 返回首页
```

### 11.2 必测场景

1. 两个讨论并行，事件/transcript/共识不串线。
2. SSE 断线后自动重连并补发，不丢消息、不重复。
3. LLM 超时/无效 JSON/空输出时，UI 有可读状态，会话不永久卡死。
4. 刷新页面后，直播/回放状态可恢复。
5. 三档屏宽下，无页面整体滚动，各区域独立滚动。
6. 前端 bundle 与网络响应中无 API Key。
7. 回放与直播的 transcript/共识/总结一致。
8. 结束讨论幂等；结束后不能继续发言。
9. 首页 5 条样例可见、可进入。
10. 主持人总结不出现 JSON 字段名。

### 11.3 质量门禁

- 核心逻辑（嘉宾生成、发言调度、共识提炼）先写测试再实现，TDD 用例可追溯
- 单元/组件/接口测试通过
- E2E 主链路通过（含断线、多会话、回放一致性）
- 5 会话/20 SSE 压力测试通过
- 无 P0/P1 缺陷
- Key 扫描通过
- README 按步骤可复现

### 11.4 开发范式映射

| 阶段 | 本项目落点 | 验收证据 |
| --- | --- | --- |
| SDD：数据建模与 API 契约 | `PRD.md`、`ER.md`、`03-API契约.md`、`04-SSE事件契约.md` | 字段/状态/错误码评审通过 |
| DDD：前端组件与页面 | `FRONTEND-PLAN.md`、`apps/web` | 三档布局、组件测试、截图 |
| TDD：核心逻辑测试先行 | 嘉宾生成、发言调度、共识提炼 | 先失败测试、再实现，测试通过 |
| E2E：系统端到端 | `e2e/`、主链路/断线/多会话/回放 | Playwright 报告 |
| Agent 行为/上下文 | `AGENT-BEHAVIOR.md`、`packages/agent`、`evals/` | 5 议题 eval 报告 |

## 13. 风险与待决

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| LLM 延迟/不稳定 | 节奏断裂 | 关闭 thinking、短 prompt、流式、超时、兜底 |
| JSON 无效/空白 | 调度/共识中断 | JSON mode + Zod + 修复重试 + 降级 |
| 多角色协作冲突 | 返工 | 契约先行、目录所有权、PM 集成 |
| 回放/直播不一致 | 可信度下降 | 共用 reducer、事件 fixture、E2E 对比 |
| UI 范围膨胀 | 延期 | P0 清单、设计 token、11/2 12:00 冻结 |
| 72h 时间不足 | 交付缺项 | 10:00 行为冻结、12:00 功能冻结、P2 全砍 |

待决：

1. 专家人数上限 6 是否合适？默认 4，允许 3–6。
2. 单场结束：以观点饱和为主，轮次只做覆盖保底与 36 轮安全上限。
3. 首页是否展示“已结束”区？P0 展示进行中 + 最近结束，避免只有空列表。
4. 是否允许用户中途插话？P1，不做。
5. 是否展示发言意图标签？仅在专家状态栏展示，transcript 保持干净。
