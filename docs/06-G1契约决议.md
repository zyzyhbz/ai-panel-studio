## 0. 裁决原则

1. **先修“会卡死/会串线/无法验收”的洞**，不追求字段完备。
2. **每个 `turn.started` 必须有终态**（completed 或 aborted），否则 UI 和回放都会悬挂。
3. **每个会话必须有终态事件**（ended 或 failed），否则前端只能无限重连。
4. **回放与直播必须同源**：`events.payload_json` 就是 SSE `data` 对象；回放走同一 reducer。
5. **可测性优先于“文档好看”**：QA 无法观测的 AC，等于没有验收。
6. **72 小时内不引入全局 SSE、不引入消息队列、不引入 ORM、不做视频/语音。**

## 1. 接受的 P0 变更

### 1.1 创建幂等

- `POST /api/discussions` 请求体新增 **`clientRequestId`**（UUID v4，必填）。
- 服务端 24h 内按 `clientRequestId` 幂等：
  - 首次创建：`201`；
  - 重复请求：`200`，返回同一条 discussion。
- 502/504 错误体 `details` 必须包含 `{ discussionId, topic, status }`。
- 目的：解决“12s 同步生成期间超时/刷新/重复点击 → 两条重复讨论”。

### 1.2 状态与列表

- 对外状态：`generating / ready / live / summarizing / ended / failed`；删除对外 `draft`。
- `GET /api/discussions?status=` 支持：
  - `all`（默认）
  - `active`（generating + ready + live + summarizing）
  - `ended`
  - `failed`
  - 也接受精确状态（如 `ready`）
- 排序固定：`active` 优先，其次 `ended`/`failed`；同组按 `updatedAt DESC, id ASC`。
- 列表返回全部 `experts`（≤6），并返回 `errorCode`、`plannedTurns`、`turnCount`。
- 所有 `/api` 响应加 `Cache-Control: no-store`。
- 首页在 `visibilityState === 'visible'` 时每 5s 轮询列表（前端约定，不新增全局 SSE）。

### 1.3 三个新持久化事件

| 事件 | 何时 | 关键字段 | 作用 |
| --- | --- | --- | --- |
| `discussion.summarizing` | 最后一条 `message.completed` 之后、`summary.completed` 之前 | `reason: user/auto`, `startedAt` | 消除自然收束时 5–20s 无解释空白 |
| `turn.aborted` | `turn.started` 后本轮无法完成 | `turnIndex`, `speakerId`, `messageId?`, `reason`, `retryable` | 清除“准备发言”悬挂，回放不卡 |
| `discussion.failed` | 会话进入终态 failed | `code`, `message`, `retryable`, `failedAt` | 前端停止重连；failed 也能回放已产生内容 |

硬约束：

- 每个 `turn.started` 后必须跟 `message.completed` 或 `turn.aborted`。
- `turn.aborted` 不计入 `turnCount`。
- `discussion.failed` 是终态事件；之后不再有 message/insight 事件。
- `failed` 允许 `POST /end`：若有 messages，进入 `summarizing`，用模板总结兜底到 `ended`；若无 messages，返回 `409`，只能重新生成或返回首页。

### 1.4 失败与降级可观测

- `message.completed.message.degraded: boolean`（默认 false）：标记该条是兜底/截断/修复产物。
- `summary.completed.summary.isFallback: boolean`：总结是否使用模板兜底。
- 总结失败也发 `discussion.ended`，`summary` 为 `null`；前端显示“总结未生成”。
- `error` 事件保留 `recoverable`；`recoverable=false` 后必须跟 `discussion.failed`。
- 错误体新增 `requestId`；响应头 `X-Request-Id`。

### 1.5 专家字段

`experts[]` 新增/改名：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `focusArea` | 是 | 原 `focus`，静态关注领域 |
| `stanceAxis` | 是 | 立场轴，如“岗位替代 vs 岗位重构” |
| `polarity` | 是 | `strong_oppose/oppose/neutral/support/strong_support` |

- `color` 在会话内唯一，并避开语义色相（共识绿、分歧红、待验证紫、强调金）。
- `stance` 保留为一句人话；机器判定用 `stanceAxis + polarity`。

### 1.6 发言与轮次

- `intent` 扩展为：`opening/probe/rebut/support/extend/clarify/mediate/redirect/summary`。
- `turn.started` 新增：
  - `messageId`（预分配，与后续 delta/completed 同一个 id）
  - `turnFocus`（原 `focus`，本轮关注点）
  - `targetMessageId?: string`（主要回应对象）
  - `references?: string[]`（被回应/串联的 messageId，可多个）
- `message.delta` 新增可选 `turnIndex`。
- `message.completed.message` 新增 `charCount`、`degraded`、`targetMessageId?`、`references?`。
- 轮次口径：
  - `turnIndex` 从 1 开始，每条 `message.completed` +1（含主持人）。
  - `plannedTurns = clamp(4 + 2 * expertCount, 8, 12)`。
  - `maxTurns = min(plannedTurns + 2, 14)`（硬上限 14）。
  - `turnCount` 只统计 completed，不含 aborted。
- `GET detail` 新增 `activeTurn`：
  ```ts
  { turnIndex, speakerId, messageId, intent, turnFocus, references } | null
  ```
  用于刷新/重连时恢复“正在说”的状态。

### 1.7 共识/分歧

- 删除 `insights.status`（MVP 不做 resolved）。
- `insight` 新增 `firstSeenTurn`（整数）。
- `updatedAt` 语义：**该条内容最后一次变化的时间**；未变化条目保留原时间戳。
- `insight.updated` 仍是全量快照；前端按 `id + content` 做高亮去抖。
- 每条 insight 至少 1 条 `evidenceMessageIds`；无依据不得进入 consensus/divergence。
- 提炼频率：至少每 2 轮一次；更新在提炼完成后 2s 内到达；失败保留旧快照，不推空。

### 1.8 回放与状态接口

- 新增 `GET /api/discussions/:id/state`：返回**由事件重放得到的投影快照**，用于 QA 验证“直播终态 = 回放终态”。
  ```ts
  { discussionId, status, turnCount, lastSeq, experts, messages, insights, summary, activeTurn }
  ```
- `GET /events` 对 `live/summarizing/ended/failed` 都可用；返回持久化语义事件，按 `seq` 升序，支持 `after/limit`，返回 `hasMore`。
- `stream.ready` 增加 `fromSeq`、`lastSeq`、`status`、`retryMs`。
- 新增无 id 的 `stream.caught_up` 事件，标记补发结束、进入实时。
- SSE 端点设置 `retry: 1000`；单会话最多 8 个 SSE 连接，超限 429。
- 对不存在/非法会话，SSE 返回 `application/json` 404，不建立流。

### 1.9 可测试性钩子（仅 mock + 非 production）

- 请求头 `x-qa-scenario`：`normal/slow/timeout/invalid-json/empty/duplicate/runaway/long/mixed`，绑定到新建会话。
- `GET /api/health` 返回：`status/version/llmMode/dbReady/activeSseCount/uptimeMs/rssBytes/now`；不返回 `dbPath`。
- 前端在 mock 模式暴露 `window.__qa.sse` 环形缓冲（最多 1000 帧），供 E2E 断言断线补发/去重。
- 服务端 mock 调用记录 `QA_LLM_LOG`（JSONL）：只记 `requestId/discussionId/kind/model/thinking/includedMessageIds/usage`，不记 prompt 全文。
- `LLM_MODE` 未设置或非法时启动失败；`real` 模式无 Key 时启动失败 `LLM_NOT_CONFIGURED`。

### 1.10 输入与安全

- topic 按**纯文本**接受，允许 `<`、`>` 等字符；限制 2–200 个 Unicode 码点。
- 前端所有用户/模型文本用纯文本渲染，禁止 `dangerouslySetInnerHTML`。
- `message.content` 为纯文本，不支持 markdown/HTML。
- 请求体上限 16KB；错误不返回堆栈/路径/Key。
- 构建后扫描 `apps/web/dist` 无 `sk-`/Key 片段。

### 1.11 LLM Adapter 归属（解决角色冲突）

采用“接口在 Agent、真实传输在 Server、Mock 在 Agent”的三段式：

| 部分 | Owner | 位置 |
| --- | --- | --- |
| `LLMClient` 接口、PromptSpec、mock client、fixtures | AI/Agent | `packages/agent/**` |
| 真实 DeepSeek HTTP、超时、重试、限流、Key 加载、错误映射 | 后端 | `apps/server/src/llm/**` |
| **运行期 mock（QA 钩子/日志）** | 后端 | `apps/server/src/llm/mock.ts` |
| **eval/单测 mock** | AI/Agent | `packages/agent/**`、`evals/**` |
| 评估脚本的 fake/real 注入 | AI/Agent | `evals/**` |

约束：

- `packages/agent` 不直接读取环境变量/Key，不直接 `fetch` 真实 API。
- 后端把 `LLMClient` 注入 agent 的纯函数；agent 不知道 transport 细节。
- 禁止出现第二套生产 HTTP 客户端。
- `evals/` 可用 mock client；真实 eval 通过后端暴露的 CLI/脚本注入，不在 agent 包内读 Key。
- **两套 mock 分工**：运行期用后端 mock（绑定 `QA_LLM_LOG`/`x-qa-scenario`）；agent mock 只给 eval/单测。不要为了“只留一套”在交付前切换运行期实现。

### 1.12 Prompt 目录

`docs/prompts/` 分两层：

```text
docs/prompts/
├── runtime/     # 生产运行时 prompt（AI/Agent owner）
└── devlog/      # 题目要求的开发过程 Prompt（AI 起草，PM 汇编进 PROMPT-LOG）
```

`docs/PROMPT-LOG.md` 只汇编 `devlog/` 中 ≥5 个阶段的记录，避免运行时 prompt 与交付用 Prompt 记录混在一起。
