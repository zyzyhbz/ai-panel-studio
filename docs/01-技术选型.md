## 0. 结论

推荐采用 **组合 A：TypeScript 全栈单仓**。

```text
React 19 + Vite + TypeScript + Tailwind CSS
                │
        SSE / REST（共享 Zod 契约）
                │
Node.js 24 + Fastify 5 + TypeScript
                │
        SQLite（WAL）+ 语义事件日志
```

一句话理由：

> 这套组合对“流式发言、事件回放、多会话隔离、结构化可视化、72 小时交付”五个关键点都没有明显短板，而且前后端同语言，能把契约、事件类型和回放 reducer 做成一份共享代码，减少四个智能体之间的接口漂移。

如果团队更偏好 Vue，**组合 B（Vue 3 + Vite + Pinia + Fastify）** 是唯一值得切换的备选；Next.js 全栈、React + FastAPI、SvelteKit 均不建议作为本次 72 小时 MVP 的主方案。

## 1. 选型约束

### 1.1 产品约束

| 约束 | 对技术栈的要求 |
| --- | --- |
| 回答快、快速碰撞 | 支持 token 级流式输出；前端能高频增量渲染而不整页重绘 |
| 观点全、结构化 | 复杂但可组合的卡片/面板/时间线；支持 SVG 或轻量图表 |
| 可随时录制、回放 | 事件持久化；直播与回放共用同一套状态还原逻辑 |
| 上下文及时共通 | 单一会话事实源；每次发言读取最新事件序列；严格按 session 隔离 |
| 过程透明 | 实时状态机、发言意图、公开摘要；不暴露隐藏 CoT |
| 议题管理 | 多会话并行；列表、状态、进度、结论可查询 |
| 中文 UI、响应式 | 三档布局；各区域独立滚动；不能依赖整页滚动 |
| 本地运行、前后端分离 | 一条命令启动；API Key 只在服务端 |

### 1.2 工程约束

- 必须在 **2026-11-02** 前交付可运行版本。
- 四个角色（AI/Agent、前端、后端、测试）由独立智能体执行，需要清晰的目录边界和契约。
- 运行环境是 Windows，脚本不能依赖 bash。
- 数据库固定 SQLite。
- 运行时模型使用 DeepSeek API，Key 只允许在配置阶段读取。
- 需要可重复的自动化测试，不能依赖真实模型做全部测试。

### 1.3 明确不做

- 视频录制/视频导出
- 语音输入/语音合成
- 登录、权限、多租户
- 云端部署与横向扩展
- 移动端原生 App
- 议题树/子议题
- 真实用户协作编辑

### 3.3 为什么不是其他组合

**C：Next.js 全栈**
- 本题不需要 SSR/SEO，Next.js 的主要优势用不上。
- App Router 的 Server/Client 边界会增加多智能体协作时的认知负担。
- Prisma + SQLite 在 Windows 上多一层引擎/生成步骤，冷启动和迁移都更重。
- 题目强调前后端分离，Vite SPA + Fastify API 的边界更干净。

**D：React + FastAPI**
- FastAPI 做 LLM 编排很舒服，但前后端两套语言会带来类型重复、契约漂移、依赖与启动脚本翻倍。
- 本次没有 Python 独有依赖，收益不足以抵消 72 小时成本。

**E：SvelteKit**
- UI 和动效上限很高，但生态、测试工具和智能体生成稳定性都不如 React。
- 本次是交付风险优先，不是技术探索优先。

**B：Vue**
- 不是“不能做”，而是 React 在组件生态、Testing Library、Playwright、智能体熟悉度上更稳。
- 若你明确偏好 Vue，切 B 的额外成本约 4–6 小时，后端和契约不变。

## 5. 关键架构决策

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| ADR-01 | 用 SSE，不用 WebSocket | 当前只需服务端→客户端推送；用户操作走 REST；SSE 更简单，断线重连语义更好 |
| ADR-02 | 持久化“语义事件”，不持久化每个 token | 回放需要的是发言、状态、共识变更；token 级日志体积大且无必要 |
| ADR-03 | 直播与回放共用同一套 reducer | 保证“回放与直播一致”，避免两套渲染逻辑漂移 |
| ADR-04 | SQLite 用 SQL migration + Repository，不上 ORM | 72 小时内减少代码生成/迁移工具风险；数据量小，SQL 可控 |
| ADR-05 | 实时发言默认 `deepseek-flash`，显式关闭 thinking | 降低首字延迟；结构化任务用 JSON mode；不让隐藏 CoT 进入 UI |
| ADR-06 | 提供 mock LLM 模式 | 测试可重复、零费用；真实 API 只做 smoke |
| ADR-07 | Key 只在服务端 `.env.local` | 不进入浏览器 bundle、不提交、不打印 |
| ADR-08 | 单进程 + 每会话队列/AbortController | MVP 足够；避免引入 Redis/消息队列；会话之间严格隔离 |

### 5.1 事件模型

建议的语义事件：

```text
session.created
roster.ready
turn.started
message.delta          # 仅实时，不落库
message.completed      # 落库
consensus.updated      # 落库
summary.completed      # 落库
session.ended
error
```

- 实时：`message.delta` 通过 SSE 推给前端，前端只更新当前消息的临时缓冲。
- 落库：`message.completed` 保存完整发言；回放时按事件顺序重放，不重放 token。
- 回放：前端用同一 reducer 消费历史事件，支持暂停/倍速/跳转；不调用 LLM。
- 断线：客户端带 `Last-Event-ID` 重连，服务端从该序号之后补发。

### 5.2 前端状态分层

```text
Zustand：当前页面、筛选、弹窗、回放速度等 UI 状态
Reducer：session 事件 → transcript / experts / consensus / status
Stream buffer：当前正在流式输出的那条消息，按帧批量刷新
```

高频 token 不直接 dispatch 到全局 store，避免整页重渲染。

### 5.3 后端会话隔离

- 每个 session 一个 `SessionRunner`，包含自己的事件序列、AbortController、队列。
- 所有查询/写入都带 `session_id`；仓储层禁止无 session 条件的“全表读”。
- 同一 session 的发言串行；不同 session 可并行。
- SQLite 开 WAL、`busy_timeout`；写事务尽量短。
- 进程重启后，从事件表恢复会话；未完成的运行标记为 `interrupted`，不自动重跑。

## 6. DeepSeek 接入

### 6.1 API 事实

根据 DeepSeek 官方文档（2026-10 当前版本）：

- OpenAI 兼容 Base URL：`https://api.deepseek.com`
- 当前模型名：`deepseek-flash`、`deepseek-v4-pro`
- `deepseek-flash` 由 DeepSeek-V4.1-Flash 提供服务；支持 JSON Output、流式输出
- thinking 模式默认开启，需要在请求中显式关闭
- JSON Output 需要设置 `response_format: {"type": "json_object"}`，并在 prompt 中写 “json” 和示例
- 如果 JSON 无法识别，API 可能返回空白内容，需要重试/修复

参考：

- [DeepSeek API Docs](https://api-docs.deepseek.com/)
- [JSON Output](https://api-docs.deepseek.com/guides/json_mode)
- [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode)
- [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing)

### 6.2 模型策略

| 任务 | 模型 | thinking | 输出 |
| --- | --- | --- | --- |
| 阵容生成 | `deepseek-flash` | 关闭 | JSON |
| 主持人开场/追问/总结 | `deepseek-flash` | 关闭 | 自然语言/JSON |
| 下一位发言决策 | `deepseek-flash` | 关闭 | JSON |
| 专家发言 | `deepseek-flash` | 关闭 | 流式自然语言，1–2 句 |
| 共识/分歧提炼 | `deepseek-flash` | 关闭 | JSON |
| 最终总结（可选高质量） | `deepseek-v4-pro` | 可开启 | 自然语言 |

默认全部用 `deepseek-flash`；`DEEPSEEK_MODEL` 环境变量可切换，禁止硬编码。实时链路不用 `deepseek-v4-pro` 的 thinking，避免首字延迟不可控。

### 6.3 成本估算

按官方 2026-10 价格，`deepseek-flash` 峰时输入 $0.30 / 1M tokens、输出 $1.20 / 1M tokens。

- 单场 10–12 轮，约 18–24 次调用
- 估算输入 10–30 万 tokens、输出 1–3 万 tokens
- 单场成本大约 **¥0.2–1.0**
- 开发期测试 + 演示总成本预计 **远低于 ¥10**，但以实际账单为准

### 6.4 Key 处理

- 现在**不读取**本机 Key 文件（路径由 PM 在配置阶段使用，不写入仓库）。
- 进入配置阶段时，由后端一次性读取，写入项目根目录 `.env.local`，权限最小化。
- `.env.local` 必须在 `.gitignore` 中；只保留 `.env.example`。
- 变量名：`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`。
- 禁止 `VITE_` 前缀；禁止日志、错误堆栈、API 响应回显 Key。
- 构建后扫描 `apps/web/dist`，确认没有 `sk-` 或 Key 片段。
- PM/测试只验证“服务端能读到”，不查看、不复制、不粘贴 Key 内容。

### 6.5 失败与降级

- 超时：单次调用 20–30s；超时中止并给出可读错误。
- JSON 无效：Zod 校验失败 → 一次修复重试 → 仍失败则使用兜底发言/跳过该轮。
- 空内容：按官方提示重试一次。
- 速率限制：指数退避；同一 session 内串行，避免瞬时打满。
- UI 永远不显示原始 JSON 或原始错误堆栈。
