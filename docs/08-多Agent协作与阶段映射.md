## 1. 我的组织方式

这个项目由我统一调度多个角色 Agent 完成：

| 角色 | 职责 | 主要产物 |
| --- | --- | --- |
| 产品经理 Agent | 需求、PRD、功能边界、验收标准 | PRD、审计、范围 |
| AI/Agent 工程师 | runtime prompt、上下文、发言策略、eval | `packages/agent`、runtime prompts |
| 前端 Agent | 页面、组件、状态、主题、SSE 客户端 | `apps/web` |
| 后端 Agent | SQLite、API、SSE、SessionRunner、恢复 | `apps/server` |
| 测试 Agent | E2E、压力、回归、发版门禁 | `e2e` |

我负责任务拆解、契约裁决、集成和验收。每个 Agent 只改自己的目录，跨目录变更必须回到我这里。

## 2. 我如何下发任务

我的调度方式是任务包：

```text
目标：这次要解决什么
输入：读哪些文档、哪个版本
边界：只能改哪些目录，不能碰什么
交付：必须产出哪些文件/结果
验收：什么算通过，什么情况必须停
```

Agent 在这套约束内展开实现级 Prompt、代码和测试。我的引导体现在四个动作：

1. **定义目标**：把产品需求翻译成可执行任务；
2. **给上下文**：指定 PRD/ER/API/SSE 版本，避免 Agent 自己猜；
3. **验收证据**：看测试、截图、URL、日志，不只看“完成了”；
4. **纠偏**：不达标就打回，给失败现象和新的验收标准。

## 3. 与 SDD / DDD / TDD / E2E 的对应

| 阶段 | 我做什么 | 谁执行 | 证据 |
| --- | --- | --- | --- |
| SDD | 下发契约评审任务，裁决并冻结 v1.0 | 后端/前端/测试 Agent | ER/API/SSE、06 决议、契约测试 |
| DDD | 定领域语言、限界上下文、事件溯源不变量 | AI/前端/后端 Agent | `AGENT-BEHAVIOR`、`debateMap`、共享 reducer |
| TDD | 给失败现象/验收，审查测试能否抓住 bug | 各实现 Agent | agent 92 / server 28 / web 42 |
| E2E | 定义用户旅程和门禁，不替测试改实现 | 测试 Agent | 35 条 Playwright |
| 多 Agent | 拆任务、定目录所有权、集成、交付 | 我 | 任务包、Git 历史、验收记录 |

这些阶段是工程检查点，同一个 Agent 会跨阶段；我负责定义任务、边界和验收。

## 4. Prompt 的两层

| 层级 | 谁写 | 例子 | 位置 |
| --- | --- | --- | --- |
| 任务/评审/验收 Prompt | 我 | G1 只做设计、BUG-01 空壳、布局 boundingBox、轮数改饱和 | `PROMPT-LOG.md` |
| 运行时/实现 Prompt | 各角色 Agent | P-ROSTER、P-DECIDE、P-SPEECH、组件测试、E2E | `docs/prompts/runtime/`、`e2e/` |

`PROMPT-LOG.md` 记录第一层；第二层作为附件保留全文。这样既能看出我如何引导，也能看出各角色实际怎么实现。

## 5. 为什么这样能保证质量

- **契约先行**：API/SSE 先冻结，多角色才能并行而不漂移；
- **目录所有权**：谁改哪里是硬约束，减少冲突；
- **可执行验收**：测试、截图、smoke 是放行条件，不靠 Agent 自述；
- **变更可追溯**：PRD、06、09、Prompt 版本、Git 提交分层；
- **失败可回归**：线上/联调发现的问题，必须补成测试再修。

这套方式让我能同时管理多个角色，而不是替每个角色写代码；我的核心工作是把目标、上下文、边界和验收定义清楚。
