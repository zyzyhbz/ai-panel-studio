## 1. 工具链与角色

本题要求描述“如何通过 Claude Code 结合 Deepseek V4 Pro 模型进行开发”。本次实际执行使用的是 **DeepSeek Harness（Vibe Coding 工具）+ deepseek-flash 模型**，没有使用 Claude Code；原因是本机可用环境与模型接入方式。

工作流本身可以等价迁移到 Claude Code：把 PM 的任务包交给 Claude Code，底层接 DeepSeek V4 Pro，角色边界、契约、测试门禁不变。实际工具不同，不影响“工程化拆解”的方法论。

团队编制：

| 角色 | 职责 |
| --- | --- |
| PM | 需求、PRD、契约、任务分派、变更控制、集成、交付 |
| AI/Agent | prompt、上下文工程、发言策略、行为 eval |
| 前端 | 演播厅 UI、交互、响应式、SSE 客户端 |
| 后端 | SQLite、API、SSE、会话运行时、持久化 |
| 测试 | 独立验收、E2E、压力、回归、发版门禁 |

四个执行角色各由一个独立智能体承担，PM 是唯一的需求入口、契约出口和集成出口。

## 2. 开发流程

采用“契约先行 + 小周期并行 + 质量门禁”的方式，而不是让四个智能体同时自由写代码。

```text
G0 需求冻结
  → G1 行为与契约冻结
    → G2 脚手架与 mock 基线
      → G3 四角色并行开发
        → G4 集成与行为调优
          → G5 硬化与回归
            → G6 交付
```

### G0：需求冻结

- 把题目、用户笔记、角色约束整理成 PRD。
- 明确 P0/P1/P2 和非目标。
- 每条 P0 有 ID、验收标准、责任角色。
- 产出：`PRD.md`、`TASKS.md`。

### G1：行为与契约冻结

- AI/Agent 交行为规范、prompt 清单、上下文预算、eval 指标。
- 后端评审 ER/API/SSE，确认状态机、事务、seq、补发可落地。
- 前端评审 UI 数据需求，确认详情 + SSE 足够支撑直播/回放。
- 测试评审 AC 可测性，指出不可观测的字段。
- PM 汇总、裁决、冻结契约 v1.0。
- **本阶段不写生产代码**，避免接口未定就返工。

### G2：脚手架与 mock 基线

- PM 建单仓、根配置、脚本。
- 后端建 SQLite migration/seed、Fastify 骨架、健康检查。
- 前端建 Vite 骨架、设计 token、App Shell。
- AI/Agent 建 `packages/agent` 骨架、prompt v1、mock evaluator。
- 测试建 Playwright 骨架、fixtures、mock server。
- 出口：一条命令启动，mock 模式下能跑通空会话。

### G3：并行开发

按垂直切片推进，每个小周期必须“可运行、可测试、可回滚”：

1. 创建讨论 + 生成阵容
2. 确认 + 主持人开场
3. 专家发言 + SSE 流
4. 共识/分歧增量更新
5. 总结
6. 回放
7. 多会话隔离
8. 响应式/异常态

目录所有权固定：

- AI/Agent：`packages/agent/**`、`evals/**`
- 后端：`apps/server/**`、`scripts/db/**`
- 前端：`apps/web/**`
- 测试：`e2e/**`
- PM：`docs/`、根配置、README

角色只改自己的目录；共享文件由 PM 统一修改；跨目录变更走 PM。

### G4：集成与行为调优

- PM 按契约合并，跑接口/组件/E2E。
- AI/Agent 用 5 个议题跑行为 eval，修 prompt/context。
- 测试独立验证 AC，不替 AI 调 prompt。
- 行为 bug 归 AI/Agent；接口/DB/SSE bug 归后端；UI/状态 bug 归前端；跨端 bug 由测试定级后分派。

### G5：硬化与回归

- 5 会话/20 SSE 压力测试（mock LLM）。
- 断线重连、重复事件、乱序、空输出、超时。
- 三档响应式、独立滚动、reduced motion。
- Key 扫描、XSS、超长输入、错误信息脱敏。
- 0 P0/P1 才允许 RC。

### G6：交付

- README、API 文档、ER 图、测试报告。
- Prompt 记录 ≥5 段，按阶段标注开发范式。
- Git 提交历史按 `docs → schema → api → ui → tests → fix` 分层。
- 邮件提交 zip + 文档 + GitHub/Gitee 邀请。

## 3. 与 AI 协同中遇到的典型问题

### 问题 1：多智能体并行，容易各写各的

**表现**：前端按自己的想象调 API，后端按自己的理解存字段，AI 角色把 prompt 写进 server，最后接口对不上。

**解决**：

- 先写 PRD/ER/API/SSE，再冻结，再并行。
- 每个角色只拥有自己的目录，不能改别人的文件。
- 每个任务包固定包含：目标、输入文档版本、允许修改目录、验收标准、测试命令、交付格式、停止条件。
- PM 统一提交，避免四个智能体同时操作 Git index。
- 变更必须走 PM：影响分析 → 升版本 → 通知四角色。

### 问题 2：LLM 输出不确定，延迟和格式都不可控

**表现**：JSON 解析失败、返回空白、发言太长、重复观点、首字慢。

**解决**：

- 实时链路默认 `deepseek-flash`，显式关闭 thinking，降低首字延迟。
- 结构化任务用 JSON Output + Zod 校验；失败一次修复重试，再失败走兜底。
- 发言限制 1–2 句、最大字符数；主持人不收尾时强制进入总结。
- 提供 mock LLM，测试不依赖真实模型；真实 API 只做 smoke。
- 用行为 eval 看 JSON 合法率、长度合规、发言分布、重复率、共识依据、延迟、成本。

### 问题 3：直播和回放容易变成两套逻辑

**表现**：直播正常，回放少消息/共识对不上；刷新后状态丢失。

**解决**：

- 事件溯源：语义事件落库，`message.delta` 不落库，`message.completed` 落库。
- 直播和回放共用同一套 reducer；回放只重放事件，不调用 LLM。
- SSE 用 `seq` + `Last-Event-ID` 补发；客户端按 `seq` 去重。
- E2E 对比直播结束状态与回放结束状态，不一致即失败。

## 4. 对“工程化 AI 开发”的理解

工程化 AI 开发不是“写一个更大的 prompt，让 AI 一次生成整个项目”。

它更像搭一条可控的生产线：

1. **拆解**：把产品拆成角色、契约、状态机、垂直切片。
2. **约束**：用 PRD、API、事件 schema、目录所有权限制 AI 的自由度。
3. **验证**：单测、契约测试、E2E、行为 eval、压力测试，每层都有证据。
4. **可观测**：日志、request/session ID、耗时、成本；出问题能定位到哪一层。
5. **可回滚**：小周期提交，契约版本化，失败可降级。
6. **上下文管理**：给 AI 的信息要“够用且最新”，不是越多越好；跨会话必须隔离。

AI 可以很快地写代码，但它不会自动对“产品是否成立”负责。PM 的价值不是写更多 prompt，而是定义正确的目标、切好边界、控制变更、用测试和证据做验收。AI/Agent 工程师的价值也不是“会写 prompt”，而是把 Agent 行为变成可重复、可评估、可回归的工程对象。
